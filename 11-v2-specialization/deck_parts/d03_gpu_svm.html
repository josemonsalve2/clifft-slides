The original GPU SVM

One interpreter, three tiers. The baseline every later generation is measured against — and, three rewrites later, still the thing to beat.

The kernel is a for(pc) switch

// hip_sampler.hip:728-731
__device__ void execute_shot(const GpuProgram& program, Rng& rng, ShotState& st) {
    for (uint32_t pc = 0; pc < program.num_instrs; ++pc) {
        const GpuInstr& instr = program.instrs[pc];
        switch (instr.opcode) {
            case OP_FRAME_CNOT: frame_cnot(st, instr.axis_1, instr.axis_2); break;
            case OP_FRAME_CZ:   frame_cz  (st, instr.axis_1, instr.axis_2); break;
            ...

Note what the CPU's computed-goto trick has become: a plain switch. There is no indirect-branch predictor on a GPU to reward threading the dispatch.

Every operand is a runtime load
instr.axis_1, instr.flags, instr.mask — all read from memory, every shot, every instruction.
st.active_k is a runtime variable
Every amplitude sweep computes its trip count as 1u << (st.active_k - 1) at runtime, and every scatter index is recomputed per amplitude.
V2 keeps the shot loop and destroys both of these. That sentence is the entire design, and §6–7 are its elaboration.

This budget is the occupancy constraint
It is where V2's first two optimizations went (§9.1). Every kilobyte reclaimed is a wave of occupancy.
Note scatter_lut
The SVM caches computed scatter indices in LDS, keyed by (axis1, axis2, k, mode). This is a runtime answer to the same problem V2 answers at compile time (§7.5).

And the SVM leaves this LUT off for the global tier — which is precisely why V2's global specialization wins so decisively (§9.3).

The cooperative reduction — where the ABI lives

Active-qubit measurement needs sum |v_i|^2 over each half of the array — a reduction across all 256 threads. Both backends implement the identical two-phase pattern (hip_sampler.hip:948, mirrored in v2_ops.h:224-262).

The comment above V2's copy is emphatic (v2_ops.h:235-236): // MUST reproduce SVM coop_reduce2's exact summation order or f64 rounding diverges at measurement branch points. — The summation order is part of the ABI. A reduction is not associative in floating point; two implementations summing the same values in different orders differ in the last bits, and a measurement near the sampling threshold then branches differently, which per §2.4 desynchronizes the PRNG forever. This single constraint rules out most of the obvious optimizations one would reach for.

What the SVM does well — this is not a strawman

Worth stating plainly, because two successor generations failed to beat it:

One kernel, compiled once
No per-circuit compile latency. No cache. No correctness gate. Ship it and it runs.
The dispatch loop keeps IR small
The bytecode is data. A 16,000-op circuit and a 4-op circuit compile to the same kernel.

V1 forgot this and paid 221-second compiles for it (§5.3).
It is heavily tuned
Four rounds, recorded in the tag history:

Hybrid

Compiling the circuit into HIP — and why, after a whole compile-cache subsystem, the answer came out noise-level.

The idea, and the used-function analysis

If the operands are known when the circuit is compiled, generate a bespoke kernel per circuit. The Hybrid backend (src/clifft/gpu/codegen/) walks the bytecode, emits HIP source with the operands as literals, and compiles it ahead of the sampling run.

Used-function analysis — kernel_codegen.h:17-50
A UsedFunctions struct with one boolean per opcode family, populated by scanning the bytecode, used to emit only the device functions the circuit actually needs.

A pure-Clifford circuit does not carry the ARRAY_U4 code at all.
A good idea
V2 keeps this. It is orthogonal to what went wrong.

Hybrid already dispatched through HSA

The awkwardness that seeded §13
Hybrid uses HIP only as a source language, then has to fight its way back out of HIP's packaging to get an object HSA will accept.

Write HIP to get a device binary → unwrap the HIP container → hand the raw ELF to HSA.

That round trip is the seed of V2's decision to drop HIP entirely.
Note -ffast-math
Hybrid was allowed reassociation. V2 explicitly is not (-ffp-contract=off, no fast-math, §6.4).

V2's correctness contract is byte-exactness against the interpreter, and fast-math would break it — for the reason §3's reduction slide gives: reassociation changes the summation order, the summation order is the ABI.
Two backends, two different answers to the same question about floating point. The difference is not taste — it is that V2 signed a contract Hybrid never did, and that contract is what makes V2's speedups checkable.

Hybrid emits a block per instruction
15 to 56 lines of HIP each. Linear in circuit size with a large constant. Not pathological — V1's is (§5) — but it means:
  • the compiler's problem grows with the circuit, so compile time does;
  • register pressure grows, because the body is one long straight-line region;
  • the win from constant operands is diluted by the volume of code the optimizer must chew through.
The lesson Hybrid teaches: per-circuit compilation is not, by itself, a performance strategy. What matters is what you emit per instruction. Hybrid emitted a block. V2 emits a call (§6.3) — and the same idea that netted Hybrid ~0% nets V2 1.3–4.0×.
Hybrid's lines-per-instruction is 15.4–55.8 and does not improve with scale. V2's converges downward to 1.00–1.27. Same input, same target, same compiler — a 14–44× difference in how much code the optimizer is handed.
