5

V1: the MLIR backend
and its failure

The generation that did not work. It is covered at length because every rule in V2's architecture exists because V1 violated it and paid.

5.1  The original idea

Hybrid proved per-circuit code generation was possible but not profitable. V1's hypothesis: the problem is the intermediate representation.

The argument
HIP source is a poor target for a code generator. Clang has to re-parse text the generator just printed, and everything interesting is buried under a general-purpose C++ frontend. Emit MLIR instead — a compiler IR designed to be produced by machines — and the generator gains direct access to the optimizer.
The stated goals — all things MLIR is genuinely good at
  • a multi-level IR where quantum structure survives into the middle end;
  • custom passes that understand EXPAND/MEAS rank algebra;
  • progressive lowering from a domain dialect down to amdgpu.
src/clifft/gpu/mlir/
bytecode
  → mlir_emit.cc   (~3,425 lines)
  → .mlir text
  → mlir-opt --canonicalize --cse \
             --convert-func-to-llvm
  → mlir-translate --mlir-to-llvmir
  → opt -O2 → llc → ld.lld
  → .hsaco
The audit checked those three goals against the artifacts
All three failed. The next three slides are the evidence, each one a measurement on emitted IR rather than a reading of a design document.

There is no multi-level IR here
V1 used MLIR as a text serialization format for LLVM IR. The op census confirms it — the emitted frame_h module is llvm.mlir.constant×240, llvm.ptr×192, llvm.shl×73, llvm.xor×68… Pointer arithmetic and bit twiddling, written in MLIR's syntax.

5.2  Finding 2: zero custom passes

mlir_codegen.cc:65-67 — and verbatim again at :172 and :239 — runs exactly three stock upstream passes:

mlir-opt --canonicalize --cse --convert-func-to-llvm
No domain dialect
Nothing above llvm was ever defined, so there was nothing to lower from.
No rank-algebra pass
EXPAND/MEAS rank tracking — the one genuinely domain-specific analysis in this problem — was never written as a pass. V2 does it in the emitter (§7.2).
No quantum-aware transform
The "progressive lowering" that motivated choosing MLIR in the first place does not exist in the tree.
This is the report's central caution, applied to our own documents. The V1 design notes describe a progressive-lowering compiler. The artifacts describe a text emitter with three stock cleanup passes. When the two disagree, the artifacts win — which is why every claim in this deck is anchored to a file and a line.

5.3  The actual failure — one line of the emitter

The choice of IR was not V1's problem. The problem is structural and visible at mlir_emit.cc:2377:

out << "  // --- Instruction sequence (" << flat.instrs.size() << " ops) ---\n";
g_emit_ak = 0;

for (size_t pc = 0; pc < flat.instrs.size(); ++pc) {
    const GpuInstr& ins = flat.instrs[pc];
That for loop is on the host, at emit time
pc is a C++ variable that never appears in the generated program. Every bytecode instruction becomes its own block of IR, so the program counter is resolved by the code generator and the GPU never has one. A circuit is not data walked at runtime; it is code.
The contrast with V2 is one character of scope
V2's emitter has the same host loop. What differs is what it writes into it: a call. 
v2_op_expand(st, v, 3u);
The device program keeps its own for over the instruction array. Same loop, different side of the compile.
This single distinction — unroll the operand sequence vs. keep it as data — separates a backend that cannot compile a 16,432-instruction circuit from one that runs it at 0.255× SVM.

The third row deserves emphasis. The build system had to detune the optimizer based on file size to make links complete at all — the constants are literal in the source:

size_t ir_bytes = llvmir.size();
const size_t kLargeIrThreshold = 4u * 1024 * 1024;   // 4 MB
const size_t kHugeIrThreshold  = 16u * 1024 * 1024;  // 16 MB
bool large_ir = ir_bytes > kLargeIrThreshold;
bool huge_ir  = ir_bytes > kHugeIrThreshold;
const char* llc_opt = huge_ir ? "-O1" : (large_ir ? "-O2" : "-O3");
When a code generator's output requires the optimizer to be turned down, the generator is the problem.

The maintainer's own rationale

mlir_kernel_cache.cc:88-92, six lines above the thresholds — this is V1's failure diagnosed correctly, in V1's own source tree:

// Large fully-unrolled circuits (surface codes emit 40MB+ IR from U2/U4
// inlining) make opt -O3 + llc -O3 take >300s. For large/huge IR we lower the
// opt level (and skip the separate opt pass) so compilation completes.
// Correctness is unaffected — only optimization aggressiveness changes.

And the detuning was not sufficient. On surface_d11_t5 the pipeline ran to completion and still produced nothing loadable:

32 seconds of compilation, then the .hsaco does not exist.

It is not a surface_d11 quirk — and it is not rank

The 10-shot correctness sweep across the whole corpus (results/fullsweep_49529.log, job 49529): 18 circuits pass, and the five that fail all fail the same way.

V1 fought the symptom — twice, locally, successfully

Two bloat sources were mitigated (reference_v1.md:243-250). Read what the fixes actually are:

OP_NOISE_BLOCK: unroll → runtime loop
Used to unroll one full site-block per site — ~1,200 sites for circuit_d5, ~100k lines / 32 MB of IR that OOM'd llc. Converted to a runtime loop over the site index.
log(x) / draw_next_noise: inline → call
Inlined at every noise draw — surface_d9_t5: 1,444 draws × ~110/~317 lines each. Hoisted to shared @clifft_log / @clifft_draw_next_noise functions.
Both fixes are the V2 principle applied locally: replace an unroll with a loop, replace an inline with a call. They worked. They were just never generalized to the thing that mattered — the instruction sequence itself.

And the unmitigated case is spectacular (mlir_emit.cc:1813,1920):

OP_ARRAY_U2incoming-frame-state branch4~150–200
OP_ARRAY_U4incoming-frame-state branchup to 16~800–1,500+
Each branch wraps a fully unrolled complex matmul. mlir_kernel_cache.cc:89-90 records the outcome in one clause: "surface codes emit 40MB+ IR from U2/U4 inlining."

Density does not grow with circuit length
The three longest circuits (1,720 → 4,296 instructions) sit at 55–69 lines/instr — essentially flat. V1's bloat was per-instruction, not super-linear in length. Which is exactly why a 418-instruction QV circuit could fail while a 4,296-instruction surface circuit compiled.

Three generations, one axis

Three code generators, one metric, and it orders them exactly as the performance results do. This is the single number that predicts whether a per-circuit generator will work: how much code do you emit per bytecode instruction? Hybrid answered ~18 and got ~0%. V1 answered 55–2,407 and could not compile. V2 answers 1.

The last row is not a slow number; it is a missing one

        --shots 10 --seed 42 --mlir
Ten shots, not ten thousand. V1 could not finish ten shots inside four minutes, on a circuit SVM completes in 0.10 s at 10,000. The job also ended with Detected 7 oom_kill events — the wall V1 hit here is memory as much as time.
A 61× slowdown is a performance result. The compile failures are a viability result — and that is the one that ended V1.

5.5  The spill claim: real, but mis-attributed

reference_v1.md:265 states that "the register-tier kernel reports private = 115 KB/thread" of spill scratch. The number is real. The tier is wrong.

The corrected attribution makes the fact more striking
The register tier never exceeded 4 KB. 115 KB is a global-tier number, on surface_d7_t19 — 27× the worst register-tier figure.
One qualification the design doc omits
Visible two lines up in the same log: that kernel was built at llc -O0 with opt skipped, because 9,967,049 bytes of IR tripped the huge-IR fallback.
So 115 KB/thread is not what the optimizer produced from V1's IR — it is what the optimizer produced after being switched off because V1's IR was too large to optimize. The two failures are the same failure, reported once each.

What the register tier actually did — VGPRs, not spills

Note the VGPR column — that is the register-tier story the scratch number was being used to tell. circuit_d3 pins 128 VGPRs, the architectural maximum, and drops to occupancy 4, while the two small circuits sit at 16 VGPRs and occupancy 8. The unrolled body does exhaust the register file. It just does so by saturating VGPRs on the register tier rather than by spilling 115 KB, and spills catastrophically only once it reaches the global tier with the optimizer disabled.

The emitter documents fighting its own IR shape

Note which way the trade-off runs (mlir_emit.cc:216-218):

// alignment=8 for coop/global tiers enables ds_read_b64 / global_load_b64
// EXCLUDED from register tier to avoid VGPR spill catastrophe (P1.9)
const char* align = (lds_amplitudes || cooperative_mode) ? " {alignment = 8 : i64}" : "";
V1 gave up wide 64-bit amplitude loads on the register tier
A real, permanent throughput loss — ds_read_b64 / global_load_b64 halve the number of memory instructions — accepted purely to keep the allocator from spilling.
That is a generator paying for its own IR shape with the hardware's memory bandwidth
The unroll did not just cost compile time. It cost runtime, indirectly, by forcing a defensive codegen choice everywhere else.
The ground rule cuts both ways. The first audit pass rejected 115 KB as unreproducible — wrong; it was looking at matrix.csv's register rows for a global-tier number. Design documents are claims rather than facts, but so is any single artifact read in isolation.

5.6  The duplication tax

By V1, every opcode was implemented three to four times — with register and coop variants doubling several of those. A fix in one did not propagate. Tracing a single opcode, MULTI_CNOT:

filerole
svm/svm_kernels.inlCPU + GPU SVM interpreter (the de-facto spec)
gpu/sampler/hip_sampler.hipGPU SVM dispatch
gpu/codegen/ops/multi_qubit_ops.incHybrid HIP-source emitter
gpu/mlir/ops/mlir_array_ops.incV1 MLIR emitter — where the bug was
gpu/mlir/v2/v2_ops_body.incV2 shared operand library
Four independent transcriptions of one gate's semantics, plus V2's. The last row is the fix: V2 adds a fifth file precisely so it can eventually be the only one.
The canonical incident
OP_ARRAY_MULTI_CNOT had px/pz swapped only in the MLIR frame update, while SVM and Hybrid were correct — corrupting the frame for every controlled measurement that followed.
Why it survived
Only cross-backend output diffing catches this class of bug — and because the GPU legitimately differs from the CPU in f32-vs-f64 rounding (§12), there is no bit-exact oracle to diff against. "Wrong" and "just f32" look alike.

The tax, made literal

The post-mortem is still inline at src/clifft/gpu/mlir/ops/mlir_array_ops.inc:428-435:

// SVM ref exec_array_multi_cnot -> exec_frame_cnot (svm_kernels.inl:502/exec_frame_cnot).
// NOTE: read pz[target] ONCE up front — the per-control pz[c] ^= pz[target]
// never touches pz[target] (target is not a control), so it stays stable;
// likewise accumulate Σ px[c] before writing px[target]. (The previous
// emission had px/pz swapped here, corrupting the frame for controlled
// measurements that follow — the circuit_d5 coop MX bug.)
Read what that comment is doing. It cites the SVM implementation by file and line as the specification, then re-derives the correct ordering by hand. That is the duplication tax made literal — the correctness of one backend maintained by a prose reference to another, checked by a human.
And note which backend was wrong
The newest one — with the most code generated per opcode. The duplication tax is not paid evenly; it is paid hardest by whichever backend emits the most.
V2's answer
A single shared operand library (v2_ops.h) compiled two ways (§6.2), which makes the interpreter and the specialized kernel byte-exact by construction rather than by testing.

5.7  The three lessons V2 is built on

1.  Never unroll the operand sequence
The bytecode is data. This is the disease, and it is the only disease — V1's choice of IR was irrelevant. A HIP-source generator that unrolled the same way would have failed the same way; V2 in MLIR would have worked.
2.  One implementation of each opcode
Divergence between backends is invisible until an output diff, and there is no exact oracle — f32-vs-f64 noise hides real bugs.
3.  Small IR is not an aesthetic preference
It is what keeps the optimizer at full strength (no size-adaptive detuning) and the register allocator able to see loop structure (VGPRs allocated for a body, not a 16,432-block chain).
